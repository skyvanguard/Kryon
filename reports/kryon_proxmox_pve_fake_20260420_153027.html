PCI PVE-2.1 — SSH allows only key-based, non-root authentication FAIL
Sección 2 · Severidad CRITICAL · Host pve_fake
Evidencia determinística
Comando ejecutado: sshd -T 2>/dev/null || cat /etc/ssh/sshd_config
Hallazgos estructurados:
{
  "PermitRootLogin": "yes",
  "PasswordAuthentication": "yes",
  "PubkeyAuthentication": "yes",
  "ClientAliveInterval": "",
  "issues": [
    "PasswordAuthentication=yes (should be no)",
    "PermitRootLogin=yes (should be no)"
  ]
}
Remediación determinística (texto de la regla)
Edit /etc/ssh/sshd_config and set: PermitRootLogin no PasswordAuthentication no PubkeyAuthentication yes ClientAliveInterval 300 ClientAliveCountMax 2 Then: systemctl restart ssh. Validate a separate sudo-enabled account works BEFORE restarting.
Contexto (LLM)
LLM NarrativaEl control PVE-2.1 es fundamental en entornos financieros que manejan datos de titulares de tarjetas, ya que el acceso SSH con autenticación basada en contraseñas o inicio de sesión como root crea vulnerabilidades de seguridad críticas. La configuración actual permite autenticación por contraseña y acceso root, lo cual viola directamente los requisitos de autenticación basada en claves. Esta configuración expone el sistema a riesgos de compromiso por fuerza bruta y ataques de tipo "privilege escalation".
Detalle de remediación (LLM)
LLM NarrativaLa edición del archivo /etc/ssh/sshd_config debe realizarse con privilegios de root, asegurándose de que las líneas PermitRootLogin, PasswordAuthentication y PubkeyAuthentication se establezcan correctamente. El parámetro ClientAliveInterval debe configurarse en 300 segundos para mantener conexiones activas y ClientAliveCountMax en 2 para cerrar conexiones inactivas. Antes de reiniciar el servicio SSH, es esencial verificar que exista una cuenta con permisos sudo funcional para evitar bloqueos de acceso al sistema.

Contexto (LLM)
LLM NarrativaEl control PVE-3.1 es fundamental en entornos bancarios y de datos de titulares de tarjetas, ya que requiere autenticación multifactor para usuarios privilegiados de Proxmox. La falta de autenticación multifactor en los usuarios administrativos representa un riesgo crítico de acceso no autorizado a sistemas críticos. Este fallo permite que un atacante que obtenga credenciales válidas pueda acceder sin restricciones a infraestructura virtual sensible.
Detalle de remediación (LLM)
LLM NarrativaPara corregir, se debe configurar TOTP como método predeterminado de autenticación multifactor en los realms 'pam' y 'pve' a través de la interfaz web. El usuario root@pam debe ser el primero en tener habilitado TFA, lo cual se realiza en la sección de permisos de usuarios. La configuración se puede validar mediante el comando CLI `pveum user modify root@pam --keys` para asegurar que el método de autenticación multifactor esté correctamente asignado.

PCI PVE-3.2 — Proxmox API tokens follow least-privilege + expiry FAIL
Sección 3 · Severidad HIGH · Host pve_fake
Evidencia determinística
Comando ejecutado: stat -c '%a %U %G' /etc/pve/priv/token.cfg 2>/dev/null ; cat /etc/pve/priv/token.cfg 2>/dev/null
Hallazgos estructurados:
{
  "mode": "644",
  "owner": "root",
  "group": "root",
  "tokens_total": 2,
  "tokens_no_expiry": 2,
  "tokens_root_pam": 2,
  "tokens_privsep_off": 2,
  "issues": [
    "2 token(s) bound to root@pam",
    "2 token(s) with no expiry",
    "2 token(s) with privsep=0 (inherits full perms)",
    "token.cfg world-permissions != 0 (mode 644)"
  ]
}
Remediación determinística (texto de la regla)
Store tokens under a dedicated non-root realm user: `pveum user add ci@pve --password ...`. Issue token with privsep: `pveum user token add ci@pve ciops --privsep 1 --expire <unix-ts>`. Enforce chmod 640 root:www-data on /etc/pve/priv/token.cfg. Rotate tokens yearly.
Contexto (LLM)
LLM NarrativaEl control PVE-3.2 es crucial en entornos bancarios que manejan datos de titulares de tarjetas, ya que los tokens de API mal configurados pueden proporcionar acceso no autorizado a sistemas críticos. La ausencia de expiración y el uso de privilegios completos para tokens vinculados a root@pam representan riesgos elevados de compromiso. Este fallo permite que credenciales persistentes sean explotadas por atacantes con acceso a los sistemas Proxmox.
Detalle de remediación (LLM)
LLM NarrativaSe debe crear un usuario dedicado llamado ci@pve para gestionar tokens de forma segura, evitando el uso directo de credenciales root. Los tokens deben ser emitidos con privsep=1 para limitar permisos y establecer fechas de expiración válidas. El archivo token.cfg debe tener permisos 640 con propietario root y grupo www-data para restringir el acceso a procesos web solo. Se recomienda rotar los tokens al menos una vez al año para mantener la seguridad.

Finalmente, se deben revisar y auditar las reglas de firewall en cada máquina virtual para garantizar que solo se permitan los accesos necesarios según las políticas de seguridad establecidas.
